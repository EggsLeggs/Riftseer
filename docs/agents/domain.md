# Domain Docs

How the engineering skills should consume this repo's domain documentation when exploring the codebase.

## Before exploring, read these

- **`CONTEXT-MAP.md`** at the repo root: it points at one `CONTEXT.md` per package. Read each one relevant to the topic.
- **`packages/<pkg>/CONTEXT.md`**: the glossary for that package's domain.
- **`docs/adr/`**: system-wide decisions. Unpublished — the Docusaurus site mounts only `docs/doc-pages/*` and `packages/*/docs`, so nothing here reaches the site.
- **`packages/<pkg>/docs/adr/`**: package-scoped decisions. These **are** published to the docs site through the package's autogenerated sidebar, so write them for a public reader.

If any of these files don't exist, **proceed silently**. Don't flag their absence; don't suggest creating them upfront. The `/domain-modeling` skill (reached via `/grill-with-docs` and `/improve-codebase-architecture`) creates them lazily when terms or decisions actually get resolved.

## File structure

This is a multi-context repo: a Bun workspace where each package owns its own domain.

```text
/
├── CONTEXT-MAP.md
├── docs/adr/                       ← system-wide decisions (unpublished)
└── packages/
    ├── types/
    │   ├── CONTEXT.md
    │   └── docs/adr/               ← published to the docs site
    ├── core/
    │   ├── CONTEXT.md
    │   └── docs/adr/
    ├── api/
    ├── web/
    └── ingest-worker/
```

`packages/raycast-extension` and `packages/reddit-bot` sit outside the Bun workspace and are not mounted by the docs site. They still take a `CONTEXT.md` if their domain needs one; put their ADRs in the root `docs/adr/`.

`packages/frontend` is dead code kept only for a CI path filter. It has no domain.

## Use the glossary's vocabulary

When your output names a domain concept (in an issue title, a refactor proposal, a hypothesis, a test name), use the term as defined in the relevant `CONTEXT.md`. Don't drift to synonyms the glossary explicitly avoids.

The root `AGENTS.md` already fixes some of this vocabulary — **user** vs **maintainer** vs **client**, and the oracle/printing split of the card model. Treat those as binding; a package `CONTEXT.md` refines them, it does not contradict them.

If the concept you need isn't in the glossary yet, that's a signal: either you're inventing language the project doesn't use (reconsider) or there's a real gap (note it for `/domain-modeling`).

## Flag ADR conflicts

If your output contradicts an existing ADR, surface it explicitly rather than silently overriding:

> _Contradicts ADR-0007 (event-sourced orders), but worth reopening because…_

The same applies to the **Invariants** section of the root `AGENTS.md`. Each one already cost the project something, and breaking one usually fails silently — contradict it out loud or not at all.
